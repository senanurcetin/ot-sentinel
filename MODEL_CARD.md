# Model card: OT-Sentinel statistical detector

## What it is

A **per-sample, weighted composite z-score** over three sensors (temperature, pressure,
vibration). For each reading it computes `|value - mean| / std` against a baseline, combines the
three with fixed weights, and maps the result to a 0-100 `risk_score`:

```
composite_z = sum_i weight_i * |x_i - mean_i| / std_i
risk_score  = round(100 * (1 - exp(-risk_score_decay * composite_z)))     # clipped to 0-100
status      = CRITICAL if risk_score >= critical_risk_threshold else SECURE
```

It also returns `anomaly_score` (a squashed max z-score kept for API compatibility) and
`per_sensor_contributions`, which say which sensors drive the score. The LLM never decides whether
a sample is anomalous; it only explains the detector's output (see [docs/architecture.md](docs/architecture.md)).

The baseline comes from the demo's own simulated "normal" envelope
(`analysis/train_anomaly_model.py`), **not from plant data**. The Isolation Forest in that script
is not used at runtime. The z thresholds (2 and 3), the weights and the decay constants are design
choices; they have not been tuned or validated against labelled attacks.

## Intended use

- Demonstrating an operator-facing anomaly workflow: detect, explain, triage, export.
- Teaching and portfolio review.

## Out of scope

- Any safety function, interlock or production monitoring.
- Connection to a live control network. See [docs/threat-model.md](docs/threat-model.md).
- Inferring the *cause* of a deviation: a fault, a failing sensor and manipulated data can look
  identical to this model.

## Evaluation

The *method* (per-sample max/weighted z-score against an attack-free baseline) was evaluated on the public
BATADAL benchmark against a static-limit rule, an Isolation Forest and a supervised reference, using all 43
benchmark signals. Results, protocol, caveats and per-attack tables are in
[`docs/case-study.md`](docs/case-study.md); the numbers are generated from `results.json` and deliberately not
repeated here.

What that evaluation does and does not cover:

- It measures the z-score *method* on BATADAL's 43 signals. The runtime code in `src/lib/anomaly-scorer.ts`
  uses 3 demo signals, a weighted sum rather than a max, and thresholds that were never fitted to BATADAL, so
  **the runtime scorer itself has not been evaluated on real attacks.**
- Results are modest (see the case study); a detector like this is a baseline, not a finished product.
- The dashboard's simulated attacks are generated far outside the normal range, so catching them says nothing
  about real attacks.

## Known limitations

- Judges each sample alone against a static baseline: no temporal context, so slow drift and small
  coordinated changes inside normal ranges can pass.
- Treats sensors independently except through the weighted sum; no cross-sensor relationships.
- No missing-data or stuck-value handling: a frozen or absent reading is not flagged.
- Network traffic volume is displayed but not scored.
- Three sensors only; the BATADAL network has many more.
