# Case study: explainable anomaly triage for OT telemetry

OT-Sentinel pairs a simple, auditable detector with an LLM that only explains the detector's verdict. This
page covers the engineering that makes that safe to use, and an offline evaluation of the detection method on
the public BATADAL attack benchmark. **The evaluation result is modest and is reported as such.** Every number
below is generated from `src/data/batadal-case-study/results.json`; none is typed by hand.

## Problem

An OT operator who gets an anomaly alert has to answer three questions fast: *is it real, which signal is
driving it, and what do I check first?* A raw score answers none of them, and an LLM that is allowed to decide
for itself whether something is an attack can invent a threat that is not there.

## Approach

1. **A deliberately simple detector decides.** Each reading is scored against an attack-free baseline
   (per-sensor z-score, mapped to a 0-100 risk score). See the [model card](../MODEL_CARD.md).
2. **The LLM only explains.** It receives the detector's verdict and the per-sensor contributions and is told
   not to dispute or re-score it ([`src/ai/flows/threat-mitigation-alert.ts`](../src/ai/flows/threat-mitigation-alert.ts)).
3. **The explanation can fail safely.** On error, timeout or rate limit the operator gets deterministic,
   rule-based triage built from the detector's own output, labelled as such
   ([`src/lib/fallback-mitigation.ts`](../src/lib/fallback-mitigation.ts)).
4. **The operator closes the loop.** Each alert can be marked "confirmed threat" or "false alarm", together with
   the risk score and the sensor that drove it. Verdicts are stored (SQLite in the Docker image) and the forensic
   report shows the false-alarm share per sensor; nothing tunes thresholds from them yet.

## Evaluation on BATADAL

**Data.** [BATADAL](https://www.batadal.net/data.html) simulates a water-distribution network (C-Town) with 43
hourly signals (tank levels, pump and valve flows and states, junction pressures). One year of attack-free data
(2014) is the reference; a second file (2016) contains attacks 1-7 and a test file (2017) contains attacks 8-14.
The files were downloaded by the repository owner and supplied by hand; their SHA-256 hashes are pinned in
[`batadal_data.py`](../analysis/batadal_data.py). They are not committed.

<!-- BEGIN results:data (generated by analysis/results_report.py) -->
- Reference (attack-free dataset03): 8761 hourly rows; 7008 used to fit, the last 1753 only to set thresholds.
- 43 signals; constant in the reference and therefore kept: S_PU1, F_PU3, S_PU3, F_PU5, S_PU5, F_PU9, S_PU9.
- False-alarm budget used for every detector: 1 alarm segment per attack-free day.
- Seed 42, scikit-learn 1.9.1.
<!-- END results:data -->

**Ground truth.** The files' own `ATT_FLAG` column cannot be used: in the 2016 file it is 1 for only a part of
each attack and **-999 ("unknown") everywhere else, with no 0 labels at all**, and the test file has no label
column. Treating -999 as "normal" would silently label most attack hours as normal. The ground truth is
therefore the *published* attack intervals ([`batadal_attacks.json`](../analysis/batadal_attacks.json)),
transcribed from the benchmark's attack tables and cross-checked: each duration equals end minus start plus one
hour, the interval hours match the files' row counts, and every `ATT_FLAG = 1` row lies inside an interval.

**Detectors.** Static limits (alarm outside the min-max seen in the reference), maximum absolute z-score,
Isolation Forest, and a supervised gradient-boosting reference trained on the 2016 file (protocol v2). Protocol v3
adds three detectors that use **time**: an EWMA of z-scores, a two-sided CUSUM, and the deviation from the
previous 24 hours ([`docs/protocol-v3.md`](protocol-v3.md)).

**Protocol** (fixed before any detection result was seen; one amendment below):

- Unsupervised detectors learn from the first 80 % of the reference year. Its last 20 % is used only to set each
  detector's threshold: the lowest one with at most one false-alarm segment per attack-free day. Every detector
  faces the same budget; no attack label can influence a threshold (a test enforces this).
- Two evaluations, reported separately: the **test file** (later in time than anything the detectors saw) is the
  headline; the 2016 file is secondary. The supervised reference is evaluated on the test file only.
- Alarm means the score is strictly above the threshold. Nothing was tuned on either evaluation file.
- **Protocol v3** was written and committed before its first run (the git history shows the order), but after the
  v2 results were known, so it is a fixed follow-up analysis rather than a strict pre-registration. Its parameters
  are textbook defaults, nothing was tuned on labelled data, and it states its decision rule in advance: a temporal
  detector counts as better than the z-score only if the 95 % day-block bootstrap interval of the paired PR-AUC
  difference on the test file lies entirely above 0. It also adds intervals to the hour-level metrics and an
  explanation-accuracy check.
- The seven signals that are constant in the reference are **kept**: pump PU3 being switched on (attacks 10-11)
  only shows up as a departure from a constant, and dropping those signals would hide it. Any such departure is
  treated as maximally anomalous.

### Protocol v3: does adding time help?

<!-- BEGIN results:v3-decision (generated by analysis/results_report.py) -->
Protocol v3 decision rule (fixed in advance in `docs/protocol-v3.md`): a temporal detector beats max absolute z-score only if the 95 % interval of its paired PR-AUC difference on the test set lies entirely above 0 (1000 day-block bootstrap resamples). Result: no temporal detector passes; there is no detectable improvement over max absolute z-score on the test set.

| Detector | PR-AUC minus max absolute z-score, 95 % interval | Better than max absolute z-score? |
|---|---:|:---:|
| EWMA of z-scores (v3) | -0.088 to 0.041 | no |
| CUSUM (v3) | -0.377 to -0.042 | no |
| 24 h rolling residual (v3) | -0.180 to -0.021 | no |
<!-- END results:v3-decision -->

No. On the test file none of the three temporal detectors passes the rule. The CUSUM and the rolling residual are
worse than the z-score, with intervals entirely below 0. The EWMA's interval includes 0. On the 2016 file the EWMA
*does* score better than the z-score, with an interval above 0, but that does not carry over to the later test file,
which is exactly why the rule looks at the test file only.

The CUSUM shows a second weakness of a segment-based false-alarm budget. Its statistic never resets, so once it
alarms it tends to stay on: it alarms in most attack-free hours of both files while still counting as only a few
alarm segments. It "catches" almost every attack hour for the same reason. The false-alarm hour fraction column,
added after the v2 amendment, is what exposes it.

### Does the explanation point at the attacked equipment?

The live dashboard tells the operator which signals drive an alarm. Protocol v3 checks whether those signals are
the right ones: for every alarmed attack hour, do the three largest per-signal scores include a signal that the
official attack description names? The attacked signals are read mechanically from the description (a tank, pump
or valve mentioned there), never from the concealment text.

For the z-score detector the answer is mostly yes. Its top three signals include an attacked one roughly three
times as often as chance on both files. The pattern per attack is what you would expect. When pump PU3 is switched
on (attacks 10 and 11), the pump's own signals lead almost every hour. When the attacker replays normal readings
for exactly the signals they manipulate (attack 8, for example), the alarm is real but its top signals are
side effects elsewhere in the network, so the explanation misses. An operator should read "which signals drive
this alarm" as a lead to investigate, not as a diagnosis. Static limits point at the right equipment about as often
as the z-score on the test file but barely above chance on the 2016 file. The CUSUM, which is on most of the time,
does no better than chance on the test file.

### How to read it

- **"Attacks caught" does not discriminate.** Every detector catches every attack, but with about one false-alarm
  segment a day an attack lasting 24-110 hours would contain an alarm by chance most of the time; the "expected
  from false alarms alone" column makes that visible. The CUSUM is the extreme case: its chance column is lower only
  because its few false-alarm segments are very long. Event recall is reported because it is the usual
  headline, not because it is informative here.
- **The hour-level columns carry the information, and they are modest.** The best detector alarms in a minority
  of attack hours and is right about half the time it alarms. Every detector that stays quiet in most attack-free
  hours catches less than half of the attack hours. The ones that catch more (the EWMA, and the CUSUM almost
  always) pay for it with many more alarms in attack-free data. Precision and PR-AUC beat the random-guess level,
  but no detector reaches both high precision and high recall.
- **Ordering.** Among the v2 detectors evaluated on both files, the maximum z-score has the highest PR-AUC, followed
  by static limits, then Isolation Forest, and of all unsupervised detectors it has the fewest alarm hours in
  attack-free data. The intervals show how fragile that is: on the test file even the z-score's lead over static
  limits is not established, because the interval of their paired difference includes 0.
- **The supervised reference does not win**, despite seeing labelled attacks, probably because the 2016 and 2017
  conditions differ from the 2014 reference and from each other; this was not investigated.
- **Attacks 10 and 11 (pump PU3 switched on, no concealment) are caught in the first hour** by the static-limit and
  z-score detectors: a signal that is constant in normal operation moves. That is an easy signature, not evidence
  about harder attacks.

### What I got wrong first (protocol amendment)

The first run produced a flattering and impossible result: the static-limit detector showed zero false alarms,
all attacks caught and zero hours to detect. It was alarming **all the time**. Two flaws in my own evaluation
caused it: the false-alarm budget counted alarm *segments*, and a permanent alarm is a single segment; and
`score >= threshold` let that detector's threshold sit on the constant floor of its scores (zero inside the
range), which switched the alarm on permanently. I fixed the alarm rule (strictly above the threshold) and
added two columns that make this class of mistake visible, the false-alarm hour fraction and the chance
baseline. No detector, signal, split or budget changed, and the first run's numbers are not used anywhere.
Because I looked at a result before making this change, the protocol is "fixed in advance, then corrected once
for a metric flaw", not purely pre-registered. A regression test now fails if the old behaviour returns.

### What the drift does to the results

One pressure signal (`P_J280`) leaves the reference range in a large share of attack-free hours in both
evaluation files, while every other signal almost never does. That share is about as large as the static-limit
detector's whole share of false-alarm hours, so most of that detector's false alarms are this one drifting signal.
Nothing was adjusted for it; it is a reminder that a baseline fitted to one year is a weak assumption.

## Findings from building the system (engineering, not detection performance)

1. **The label column was not what its name suggests** (see Ground truth): a loader that read `-999` as "unlabeled
   rows to drop" would have trained and evaluated on attack rows only.
2. **My own metric could be gamed by a degenerate detector** (see the amendment above).
3. **The demo's "normal" data raised false CRITICAL alarms.** The live demo's baseline was fitted on Gaussian
   draws but its generator sampled the normal ranges uniformly and rounded vibration to two decimals; in a
   200,000-draw simulation about 0.37 % of normal samples crossed the CRITICAL line, roughly one false alarm every
   4-5 minutes. Drawing the way the baseline was fitted reduced it to about 0.002 %, and a seeded test now fails
   if that regresses ([`src/lib/telemetry-source.test.ts`](../src/lib/telemetry-source.test.ts)).
4. **The alert dialog re-asked the LLM every second.** Fresh telemetry handed it a new object each tick, so with
   a slow model one alert cost several model calls. It now asks once per alert and discards late answers.

## Limitations

- Seven attacks per evaluation file; differences between detectors are anecdotes.
- BATADAL is a simulation of one network. Results do not transfer to real plants or protocol-level attacks.
- The 2016 and 2017 files are rounded to two decimals; the 2014 reference is not.
- Time to detect counts from the published attack start. For attacks that conceal themselves with a replay of
  normal readings, the sensor-visible effect can begin later.
- The live dashboard's scorer is a 3-signal demo with a weighted sum and thresholds that were not fitted to BATADAL.
  **This evaluation measures the method on 43 signals, not that code.**
- The live dashboard's detector is per-sample and static. Three temporal variants were evaluated (protocol v3) and
  none improved on the test file. There is no missing-data or stuck-value check.
- No authentication in the demo; it must not face an untrusted network.
